# B1-Way Account & Settings delivery

This feature belongs to `b1-way-personal`. It uses the existing Next.js shell, Better Auth identity/session/credential machinery, Drizzle/Neon database, FinanceSelect, Gym controls and blue/orange CSS tokens. No new authentication system or language-learning entitlement is introduced.

## Implemented storage and access

Account preferences and notifications are owned, product-scoped JSON with revision-based compare-and-save. Finance stores explicit nullable currency: historical entries without recorded currency remain unassigned. All totals and exports keep currencies separate; amounts use integer minor units. Investments and new Momentum investment rules use USD. Legacy non-USD investments stay visible, excluded from USD totals, with unsupported/unpriced status. Existing goals are not converted. Gym stores canonical kg/km and historical load conventions; display preferences are independent. Open forms freeze their input units. New weekly goal rules snapshot week-start preference; older rules retain Monday behavior. Calendar placement stays date-only and timestamps stay UTC.

Membership rows separate trial dates, provider-confirmed paid periods, renewal status, grace and checkout/reconciliation leases. Verified signup automatically initializes one 14-day trial per stable user/product before sign-in and redirect. Trial dates are anchored to account creation; concurrent requests and interrupted-registration retries cannot reset them. Existing paid periods and used trials are preserved. Existing accounts with unused trials retain the manual claim action. Stripe never supplies a second trial. Core writes use a central owned server guard. Settings, security, billing, private reads/export/delete/support remain available after expiry. Only canonical workouts/focus sessions already active before expiry can finish within 24 hours. Removing plans or expiring access never deletes recorded history.

Production always enforces stored trial and paid-access expiry. `B1_WAY_ENFORCE_MEMBERSHIP` only controls local development; a copied `false` value cannot bypass expiry in production. Existing explicitly configured legacy-created-before/access-until windows remain supported. Requesting an email code does not start a trial; successful verified account creation does.

Successful registration opens Momentum (`/account/momentum`). Account & Settings shows the current trial or paid membership, days remaining, and the exact end or renewal date in the user's saved timezone and date format. The same summary appears under Membership & billing. Its countdown updates each minute and when returning to the page; the final day displays “Less than a day left” and expiry never displays negative days. Payment confirmation refreshes both summaries from the server's confirmed membership status.

## Migration, audit and rollback

Run `node scripts/migrate-account.mjs` for counts and social/password migration totals. Run `node scripts/migrate-account.mjs --apply` for a consistent, encrypted row backup followed by additive DDL. Backups and keys are ignored by Git. Move the encryption key into separate operator storage with restricted access. This row backup is not a replacement for a full schema/roles `pg_dump` or provider point-in-time backup; arrange and test those before production cutover.

`lib/db/0021_account_membership.sql`, typed schema and Drizzle snapshot/journal describe the new tables. The existing database had 20 migration records while the journal had 21 prior entries; the additive runner deliberately does not invent historical migration confirmations. Before using generic `drizzle-kit migrate` on that database, reconcile its previous manually applied migrations against the database and hashes. Never replay old non-idempotent migrations blindly. The account SQL itself is idempotent.

Audit on this development database: 5 users, 3 credential accounts and **2 identities requiring social-to-password migration**; 1,650 finance entries had no stored currency. IDs and all old records remain unchanged. The audit does not print emails, password hashes, tokens or provider secrets. Do not retire the migration-only social backend until both social identities have proved their mailbox and used the library recovery flow to add credentials to their existing IDs. Login UI is email/password only; social linking and new social identity creation are blocked. Set `SOCIAL_PASSWORD_MIGRATION_COMPLETE=true` only after an approved audit. For unverified/conflicting mailboxes, use support-assisted identity proof; do not merge by email or create a duplicate user.

Avatar UI/upload/remote image allowlists and Cloudinary dependency were removed. `user.image` stays for auth schema compatibility; old external assets are not deleted. The compatibility upload action rejects authenticated old tabs. Initials are used instead.

Rollback: disable new purchases operationally, stop the jobs and roll back the application deployment while retaining additive columns/tables. Preserve settings, trials, tombstones, ledger and outbox data. Production enforcement is not controlled by an approval switch. Never roll back a paid membership by erasing billing associations. A destructive database restore requires an operator-reviewed restore rehearsal and provider reconciliation. No cloud assets were deleted by this implementation.

## Email verification and request limits

Registration presents Email, Password, Confirm password, Date of birth and the Terms/Privacy checkbox in that order. Passwords must match and remain in memory while the mailbox is verified; they are not included in verification-email requests. The display name initially comes from the verified email and can be edited in Account & Settings. Date of birth is a required, valid date on or before today and is stored as a date-only value in `user.date_of_birth`, inside the existing identity/credential transaction. It is excluded from auth/session responses and included in the user's private data export. Existing accounts retain a nullable birth date; no dates are invented or backfilled.

Before deploying this registration update, run `node scripts/apply-registration-schema.mjs --apply`. It applies the idempotent `0032_registration_birth_date.sql` column and checks that existing account fields are preserved. This migration was applied to the configured development database on 2026-10-04; all five existing accounts were preserved.

Registration validation on 2026-10-04: all 377 tests, TypeScript, full ESLint (zero warnings) and the production build passed. The new disposable PostgreSQL test exercises the actual Better Auth/Drizzle transaction, including rollback, private auth output, valid dates and existing accounts. Browser checks confirmed field order, keyboard focus, an unchecked agreement and no horizontal overflow at a 390 px viewport; existing account access still loaded. Screenshots are in `docs/qa-artifacts/registration-fields.jpg` and `registration-phone.jpg`. No real verification email or new configured-database account was created during these checks.

Configure the exact names in `.env.example`; keys are intentionally blank. Missing configuration produces an unavailable state, not a magic code or bypass. Resend sender/reply-to default to `support-mf@b1-way.pl`. Verify the sending domain in Resend and configure its actual SPF/DKIM records, then a reviewed DMARC policy. Resend sending does **not** create a receiving support inbox: configure and test that mailbox separately. No DNS or mailbox changes were performed.

Signup, recovery and account email requests validate the request origin against APP_URL and use shared database request limits. Email verification codes, resend cooldowns and guess limits remain required; no external CAPTCHA widget or provider keys are needed. Do not trust arbitrary forwarded IP headers; a single conservative untrusted-source bucket is used without a configured safe ingress. Twenty daily email slots are reserved for recovery/security so anonymous requests cannot consume the entire delivery budget. Every request/recipient/global budget lives in shared database storage, never just in process memory.

Codes are six numeric digits, 10-minute lifetime, with a 60-second cooldown. Signup allows initial delivery plus one resend. The 24-hour send block begins at the **second accepted queue reservation**. Only the latest code works. Each code permits 5 incorrect guesses and each recipient/purpose has a 10-attempt daily cap. Attempts are bound to an HttpOnly proof cookie and owner/purpose; proof is consumed by compare-and-swap before auth identity creation. Concurrent attempts cannot create multiple credentials. Registration creates identity/credential inside the supported auth-adapter transaction. A failed/ambiguous final registration directs the user to sign-in/recovery rather than claiming success or creating another ID.

Outbox content is AES-GCM encrypted; recipient/code/proof keys use keyed hashes, with a distinct server secret. Accepted delivery is durable, leased and retried with identical payload/code/idempotency key within Resend's 24-hour idempotency window. Ambiguous failures never rotate codes. Known validation/key rejections release the corresponding current recipient delivery count. Expired/exhausted payloads are cleared by the worker. Resend bounce/complaint events create shared team-scope suppressions. Configure signed webhook delivery to `/api/email/webhook`; missing/bad signatures fail closed. Authentication/security communications are separate from internal reminders. Password changes that succeeded are not falsely reported as failures when their notification transport is unavailable; the UI reports the delivery limitation.

New password/change/reset flows enforce 8–128 characters and reject a password made of one repeated character. Password scoring is advisory in the browser; no breach-check service blocks registration or password changes. Older valid credentials remain usable at login. Native signup/reset/OTP/magic-link/linking routes cannot bypass trusted server context. Native recovery uses a library-generated single-use mailbox link plus an atomic claim, revokes sessions and migrates the same stable user ID. Email change requires current-password reauthentication and proof of the new address before the library updates it; other sessions are revoked.

## Stripe setup and launch

Create **one personal-development product** with four annual recurring, quantity-one, inclusive-tax prices: PLN 3999 minor units, GBP 999, EUR 999, USD 999. Map each reviewed Price ID to the matching server environment variable. New purchases select currency automatically from trusted regional detection: PL → PLN, GB → GBP, US → USD, otherwise EUR. Missing/unknown detection uses EUR. Existing paid subscriptions keep their recorded currency. The user requested regional currency selection without a manual billing selector. Finance display preferences are separate. No client Price ID/amount/customer/product/return URL is accepted. Enable required cancellation/invoice/payment-method tools in a named hosted Customer Portal configuration. Decide applicable merchant registration, inclusive tax and automatic tax behavior with the operator; do not pretend that enabling an API flag satisfies tax/legal obligations.

Use test keys and Stripe CLI signed forwarding to `/api/billing/webhook`. Subscribe to checkout completion/expiry, subscription create/update/delete, invoice paid/payment-failed/payment-action-required, charge refunded and dispute events. Configure the endpoint with an API version compatible with the installed Stripe SDK. Current reconciliation reads annual periods from subscription **items** and invoice parent/line pricing objects; it never adds a local 365 days. Verify the SDK-version mapping in the installed types when upgrading.

Checkout/customer creation uses stable ownership metadata and idempotency keys, with leased per-user operations. Repeated requests recover the original hosted checkout; ambiguous operations cannot start a second subscription. A return URL alone never grants paid access. Verified webhook events are durable and deduplicated, then the current owned provider state is retrieved under a fenced per-member lease. Queued processing handles delayed/out-of-order delivery and retries; failures retain the last confirmed access. The first failed invoice grants no paid access. Renewal grace is absolute, bounded and once per provider period. Cancellation preserves the confirmed paid-through date. Refunds/disputes set operator-review status; a verified full refund/dispute revokes only the affected source. History is retained and another product is never canceled. Stripe owns financial receipts; Resend owns authentication/security mail, avoiding duplicate payment receipts.

Live checkout requires actual provider configuration: secret key, matching product and annual prices, signed webhook secret, cancellation portal and public Terms/Privacy URLs. The old launch/tax approval variables are ignored. Price and provider-environment verification still run before checkout or paid access. Automated checks simulate providers; no live charges, refunds or tax changes were performed in this update.

## Jobs, notifications and privacy

Schedule authorized **POST** `/api/account/jobs`, normally every five minutes, with `Authorization: Bearer <CRON_SECRET>`; secret must be at least 32 characters. There is no unauthenticated GET side effect. Steps process retryable deletion, billing events, internal-inbox reconciliation and the authentication/security mail queue independently; a failed step returns retry-required/503 without exposing recipient/provider payloads. Monitor failed queue rows and provider reconciliation errors. Internal-inbox reconciliation uses bounded queued work and fenced source revisions; it does not enqueue reminder mail.

The current notification contract is a persistent INTERNAL inbox: see [internal-notifications.md](internal-notifications.md). Explicit timed event/workout reminders use their selected lead time; untimed events do not receive fabricated morning reminders. Actual completion, goals, Journeys and weekly-review candidates use canonical owned sources and availability windows. Source revisions, completion, expiry, quiet hours and deletion are rechecked during reconciliation. Notification, support, goal and review flows send no app-reminder email or push; authentication/security mail and billing-provider receipts remain separate. Worker downtime can delay availability; it does not fabricate completion. Inbox snooze is not implemented.

Owned exports include settings, finance/currencies, investments, Gym, To-Do, Events, Momentum, legal evidence, persistent inbox message/read/archive state, legacy owned notes/likes and product access dates. They exclude password hashes, sessions/tokens, API keys, customer/provider IDs and other users. Export is an authenticated server action returning a private JSON download, with no public export URL. Finance CSV escapes formula-like strings. Export schema 3 requires the reviewed internal-inbox table; the stabilization audit did not apply its migration.

Deletion requires the current password, explicit typed confirmation and consent to stop future charges. A durable product tombstone makes pending deletion read-only. It expires pending checkouts and stops renewals before removing owned identity/data. Provider outages keep the retryable request intact. Late provider events cannot recreate an identity. Shared cross-product identities require operator review rather than deleting unrelated memberships. Provider financial records and backups may remain under the reviewed retention policy; no invented universal retention period or instant backup deletion is promised. Publish the retention policy and configure operational cleanup before launch. If EMAIL_PROTECTION_SECRET is rotated, resolve queued mail and migrate suppression keys first. The tombstone is not a perpetual account-abuse tracking score.
