# B1-Way Account & Settings delivery

This feature belongs to `b1-way-personal`. It uses the existing Next.js shell, Better Auth identity/session/credential machinery, Drizzle/Neon database, FinanceSelect, Gym controls and blue/orange CSS tokens. No new authentication system or language-learning entitlement is introduced.

## Implemented storage and access

Account preferences and notifications are owned, product-scoped JSON with revision-based compare-and-save. Finance stores explicit nullable currency: historical entries without recorded currency remain unassigned. All totals and exports keep currencies separate; amounts use integer minor units. Investments and new Momentum investment rules use USD. Legacy non-USD investments stay visible, excluded from USD totals, with unsupported/unpriced status. Existing goals are not converted. Gym stores canonical kg/km and historical load conventions; display preferences are independent. Open forms freeze their input units. New weekly goal rules snapshot week-start preference; older rules retain Monday behavior. Calendar placement stays date-only and timestamps stay UTC.

Membership rows separate trial dates, provider-confirmed paid periods, renewal status, grace and checkout/reconciliation leases. Trial acceptance is an atomic, once-only operation per stable user/product. Default is 14 days; only 7 or 14 is supported. Existing trials never change when configuration changes. Stripe never supplies a second trial. Core writes use a central owned server guard. Settings, security, billing, private reads/export/delete/support remain available after expiry. Only canonical workouts/focus sessions already active before expiry can finish within 24 hours. Removing plans or expiring access never deletes recorded history.

During migration, `B1_WAY_ENFORCE_MEMBERSHIP=false` preserves access. This is a launch transition, not an advertised perpetual free tier. Configure a deliberate legacy-created-before boundary and fixed access-until window before enforcement. No guessed lifetime grants, backdated charges or email-request-triggered trials are created.

## Migration, audit and rollback

Run `node scripts/migrate-account.mjs` for counts and social/password migration totals. Run `node scripts/migrate-account.mjs --apply` for a consistent, encrypted row backup followed by additive DDL. Backups and keys are ignored by Git. Move the encryption key into separate operator storage with restricted access. This row backup is not a replacement for a full schema/roles `pg_dump` or provider point-in-time backup; arrange and test those before production cutover.

`lib/db/0021_account_membership.sql`, typed schema and Drizzle snapshot/journal describe the new tables. The existing database had 20 migration records while the journal had 21 prior entries; the additive runner deliberately does not invent historical migration confirmations. Before using generic `drizzle-kit migrate` on that database, reconcile its previous manually applied migrations against the database and hashes. Never replay old non-idempotent migrations blindly. The account SQL itself is idempotent.

Audit on this development database: 5 users, 3 credential accounts and **2 identities requiring social-to-password migration**; 1,650 finance entries had no stored currency. IDs and all old records remain unchanged. The audit does not print emails, password hashes, tokens or provider secrets. Do not retire the migration-only social backend until both social identities have proved their mailbox and used the library recovery flow to add credentials to their existing IDs. Login UI is email/password only; social linking and new social identity creation are blocked. Set `SOCIAL_PASSWORD_MIGRATION_COMPLETE=true` only after an approved audit. For unverified/conflicting mailboxes, use support-assisted identity proof; do not merge by email or create a duplicate user.

Avatar UI/upload/remote image allowlists and Cloudinary dependency were removed. `user.image` stays for auth schema compatibility; old external assets are not deleted. The compatibility upload action rejects authenticated old tabs. Initials are used instead.

Rollback: keep enforcement/live charging off, stop the jobs and roll back the application deployment while retaining additive columns/tables. Preserve settings, trials, tombstones, ledger and outbox data. Never roll back a paid membership by erasing billing associations. A destructive database restore requires an operator-reviewed restore rehearsal and provider reconciliation. No cloud assets were deleted by this implementation.

## Email and bot protection

Configure the exact names in `.env.example`; keys are intentionally blank. Missing configuration produces an unavailable state, not a magic code or bypass. Resend sender/reply-to default to `support@b1-way.pl`. Verify the sending domain in Resend and configure its actual SPF/DKIM records, then a reviewed DMARC policy. Resend sending does **not** create a receiving support inbox: configure and test that mailbox separately. No DNS or mailbox changes were performed.

Signup requests need server-verified Turnstile action `b1_signup` and the trusted APP_URL hostname. Other actions are `b1_recovery`, `b1_email_change`, `b1_verify_account`. Do not trust arbitrary forwarded IP headers; a single conservative untrusted-source bucket is used without a configured safe ingress. Twenty daily email slots are reserved for recovery/security so anonymous signup and optional reminders cannot consume the entire delivery budget. Every request/recipient/global budget lives in shared database storage, never just in process memory.

Codes are six numeric digits, 10-minute lifetime, with a 60-second cooldown. Signup allows initial delivery plus one resend. The 24-hour send block begins at the **second accepted queue reservation**. Only the latest code works. Each code permits 5 incorrect guesses and each recipient/purpose has a 10-attempt daily cap. Attempts are bound to an HttpOnly proof cookie and owner/purpose; proof is consumed by compare-and-swap before auth identity creation. Concurrent attempts cannot create multiple credentials. Registration creates identity/credential inside the supported auth-adapter transaction. A failed/ambiguous final registration directs the user to sign-in/recovery rather than claiming success or creating another ID.

Outbox content is AES-GCM encrypted; recipient/code/proof keys use keyed hashes, with a distinct server secret. Accepted delivery is durable, leased and retried with identical payload/code/idempotency key within Resend's 24-hour idempotency window. Ambiguous failures never rotate codes. Known validation/key rejections release the corresponding current recipient delivery count. Expired/exhausted payloads are cleared by the worker. Resend bounce/complaint events create shared team-scope suppressions. Configure signed webhook delivery to `/api/email/webhook`; missing/bad signatures fail closed. Security communications are separate from optional reminders. Password changes that succeeded are not falsely reported as failures when their notification transport is unavailable; the UI reports the delivery limitation.

New password/change/reset flows enforce 15–128 characters, common-password scoring and server-side Have I Been Pwned range checking using only a hash prefix with padding. Safety-check outages fail closed before changing credentials. Older valid credentials remain usable at login. Native signup/reset/OTP/magic-link/linking routes cannot bypass trusted server context. Native recovery uses a library-generated single-use mailbox link plus an atomic claim, revokes sessions and migrates the same stable user ID. Email change requires current-password reauthentication and proof of the new address before the library updates it; other sessions are revoked.

## Stripe setup and launch

Create **one personal-development product** with three annual recurring, quantity-one, inclusive-tax prices: PLN 4000 minor units, EUR 1000, USD 1000. Map each reviewed Price ID to the matching server environment variable. No client Price ID/amount/customer/product/return URL is accepted. Enable required cancellation/invoice/payment-method tools in a named hosted Customer Portal configuration. Decide applicable merchant registration, inclusive tax and automatic tax behavior with the operator; do not pretend that enabling an API flag satisfies tax/legal obligations.

Use test keys and Stripe CLI signed forwarding to `/api/billing/webhook`. Subscribe to checkout completion/expiry, subscription create/update/delete, invoice paid/payment-failed/payment-action-required, charge refunded and dispute events. Configure the endpoint with an API version compatible with the installed Stripe SDK. Current reconciliation reads annual periods from subscription **items** and invoice parent/line pricing objects; it never adds a local 365 days. Verify the SDK-version mapping in the installed types when upgrading.

Checkout/customer creation uses stable ownership metadata and idempotency keys, with leased per-user operations. Repeated requests recover the original hosted checkout; ambiguous operations cannot start a second subscription. A return URL alone never grants paid access. Verified webhook events are durable and deduplicated, then the current owned provider state is retrieved under a fenced per-member lease. Queued processing handles delayed/out-of-order delivery and retries; failures retain the last confirmed access. The first failed invoice grants no paid access. Renewal grace is absolute, bounded and once per provider period. Cancellation preserves the confirmed paid-through date. Refunds/disputes set operator-review status rather than deleting history or canceling another product. Stripe owns financial receipts; Resend owns security/optional reminder mail, avoiding duplicate payment receipts.

Live checkout is blocked unless `STRIPE_LIVE_LAUNCH_CONFIRMED=true`, reviewed tax setup, portal configuration and published terms/privacy URLs are all present. Defaults keep live billing disabled. No live products, charges, refunds or tax settings were configured or tested in this run.

## Jobs, notifications and privacy

Schedule authorized **POST** `/api/account/jobs`, normally every five minutes, with `Authorization: Bearer <CRON_SECRET>`; secret must be at least 32 characters. There is no unauthenticated GET side effect. Steps process retryable deletion, billing events, optional reminder candidates and mail queue independently; a failed step returns retry-required/503 without exposing recipient/provider payloads. Monitor failed queue rows and provider reconciliation errors. Fair notification scanning rotates through the oldest checked opted-in accounts in bounded batches.

Event reminders cover unfinished current-day manual events: timed events within an hour, date-only events between 09:00–12:00. Goal reminders reuse real recorded goal evaluations and their schedules. Weekly review reminders are offered after 18:00 on the saved week's last day, until a non-draft review exists. A trial reminder is offered in its final 48 hours. In-app notices follow preference/quiet hours. Email requires verified email and explicit channel opt-in; it is deduplicated by stable reminder key. The worker rechecks completion, quiet hours, channel and deletion state immediately before delivery. Marketing consent is saved but no marketing campaign is sent. Worker downtime can delay reminders; it does not fabricate completion.

Owned exports include settings, finance/currencies, investments, Gym, To-Do, Events, Momentum, legacy owned notes/likes and product access dates. They exclude password hashes, sessions/tokens, API keys, customer/provider IDs and other users. Export is an authenticated server action returning a private JSON download, with no public export URL. Finance CSV escapes formula-like strings.

Deletion requires the current password, explicit typed confirmation and consent to stop future charges. A durable product tombstone makes pending deletion read-only. It expires pending checkouts and stops renewals before removing owned identity/data. Provider outages keep the retryable request intact. Late provider events cannot recreate an identity. Shared cross-product identities require operator review rather than deleting unrelated memberships. Provider financial records and backups may remain under the reviewed retention policy; no invented universal retention period or instant backup deletion is promised. Publish the retention policy and configure operational cleanup before launch. If EMAIL_PROTECTION_SECRET is rotated, resolve queued mail and migrate suppression keys first. The tombstone is not a perpetual account-abuse tracking score.

## Verification and remaining external work

`npm test`, `npx tsc --noEmit`, `npm run lint`, `npm run build` are the normal checks. `node scripts/check-account-integration.mjs --isolated` tests real atomic quotas/code rotation/proof consumption/trial races inside a uniquely named temporary schema; it rejects unscoped queries and never calls delivery/payment providers. Provider adapters are mocked in unit tests. Browser QA uses the existing account without sending mail or buying membership.

Run provider end-to-end tests with **dedicated test** recipients/Stripe customers/Test Clocks: verified registration, social migration, signed replay/out-of-order webhook, renewal failure/action-required and recovery, cancellation through paid end, grace expiry, refunds/disputes, repeated checkout, failed/suppressed delivery and account deletion during pending billing. External provider credentials, DNS, receiving inbox, merchant/tax/policy review, scheduler installation and Test Clock journeys remain operator work. Do not enable live billing or enforcement merely because local tests passed.
